执行摘要
  本设计书面向中国大陆求职市场，在既有开源简历工程的基础上定义“基于大模型内容生成的在线简历生成系统”。核心结论是：以结构化简历数据为内核，以大模型补丁提案为生成方式，以可审批、可追溯、可回滚为约束边界，补齐国内字段体系、中文模板族、DOCX 与结构化文本交付、生成式 AI 合规四项能力。

2 项目背景与产品定位
本章从国内市场背景出发，梳理用户痛点、竞品格局与产品差异化定位，明确系统要解决的问题边界与目标用户画像。
2.1 国内市场背景
国内求职市场在过去三年发生了三个结构性变化，这三点共同构成了本系统的立项基础。
第一，投递量级上升，筛选时间被极度压缩。 校招季头部企业单岗位简历接收量可达数千份，HR 初筛阶段留给单份简历的时间通常只有数秒。这意味着简历必须在极短时间内完成"关键词命中 + 亮点识别"两件事，而大量候选人的简历在结构与表达上并未针对这一现实做过优化。
第二，大模型能力已具备"结构化改写"质量线。 当前主流大模型已能稳定完成"流水账经历 → STAR 结构化表述""职责描述 → 成果描述""口语化自我评价 → 书面化自我评价"这类改写任务，且改写质量足以通过专业 HR 的阅读检验。这为"AI 参与简历生产"提供了能力前提。
第三，用户已经在用通用大模型替代专业工具。 大量求职者当前的实际做法是：把简历文本粘贴进通用对话式大模型，要求"帮我润色"。这种做法存在三个明确缺口——不知道缺什么（缺少基于岗位与行业的结构化诊断）、改完无处安放（模型输出的是纯文本，用户还需手工回填到模板中）、无法保证真实（模型容易补充用户并未提供的数据）。这三点正是本系统的产品机会。

典型场景
零基础起步：用户上传课程表与一份旧简历，选择"互联网产品经理 - 校招"方向，系统在 3 分钟内生成一份含教育、实习、项目、技能四大板块的初稿，用户逐条确认后导出 PDF 与 DOCX。

导入优化：用户上传一份排版混乱的 PDF 简历，系统解析为结构化数据、重建排版，并给出 12 条改进建议。
持续迭代：用户与大模型助手对话"把第二段实习的第三条改得更强调数据结果"，助手提出补丁提案，用户预览 diff 后批准，简历即时更新并生成版本快照。
2.6 设计原则
数据与表现分离：简历内容以结构化 JSON 存储，排版由模板与样式规则渲染。任何格式变更都不应触碰内容数据。
AI 只提案、不直写：大模型对简历的任何改动必须以"补丁提案"形式提交，经用户审批后落库。
真实性优先于表现力：宁可少写一句，不可编造一项。所有涉及时间、数据、职称的内容必须有用户输入来源。
可回滚：任何一次 AI 编辑、模板切换、导入操作都生成不可变版本快照。
接口可用性优先于参数丰富度：所有导出格式必须能在国内主流 Word 版本（含 WPS）中正常打开且不乱码。
环境与运行时隔离：PDF 渲染、浏览器 API、大模型调用分别落在明确的包边界内，不越界引用。

维度
国内系统典型行为
对排版设计的约束

对双栏布局的读取顺序常出错
需提供 " 单栏  ATS  友好版 " 模板
表格内容
表格内的经历条目易丢失
关键经历信息不得置于表格中
图片文字
简历照片与图标会被忽略或误判为文字

4.5 关键技术决策
决策一：简历数据用 JSONB 整体存储，而非拆表。 简历是一个高度可变、结构嵌套的文档对象，拆表会导致读取时需要大量 JOIN 且不利于版本快照。以 JSONB 存储整体文档、以数据库列存储可检索的元信息（名称、标签、可见性、归属人），是最优平衡。
决策二：大模型输出以 JSON Patch 承载。 相比让模型直接输出整份简历 JSON，补丁提案有三个优势：改动范围最小、用户可逐条审批、天然支持回滚与审计。这一机制在现有工程中已实现并验证。
决策三：预览与导出分离。 编辑器内预览使用 PDF 画布渲染，导出使用独立渲染路径。二者共享同一套 React PDF 模板组件，保证所见即所得。
决策四：富文本以受限 HTML 存储。 摘要与经历的描述字段存储 HTML 片段，渲染前经白名单清洗，避免 XSS 与渲染器不兼容。

5.3.2 上下文编排
大模型生成质量取决于上下文质量。系统采用三源上下文编排模型。
来源一：用户画像与简历结构化数据。 包含用户当前简历的全部结构化字段、历史投递记录、目标岗位偏好、地域与薪资期望。此部分为高可信上下文，直接注入提示词。
来源二：JD 结构化解析结果。 用户提供的 JD 文本经解析后得到结构化的岗位画像：岗位名称、职级、必备技能、加分技能、经验年限要求、学历要求、行业领域、软性要求、职责关键词。JD 文本属于外部不可信输入，注入前必须经过注入攻击检测与长度截断。
来源三：行业与岗位知识库（RAG）。 面向国内市场的岗位关键词库、行业术语库、成果量化表达库。例如"互联网运营"岗位的常见量化维度为 GMV、用户增长、转化率、留存率、内容播放量；"算法工程师"岗位的量化维度为模型指标提升、QPS、时延、数据规模。该知识库用于提升生成内容与岗位语境的贴合度，以及为量化追问提供候选维度。
上下文容量控制：采用分层裁剪策略——用户画像与 JD 解析结果完整注入；简历全文按分区权重注入，高权重分区（目标岗位直接相关）完整注入，低权重分区注入摘要；知识库按相似度检索注入 Top-K 条目。
5.3.3 真实性约束机制
真实性是本系统区别于通用大模型的关键，需在四个层面同时落地。
（1）来源标签。 结构化简历数据中，每条可生成长文本字段（自我评价、经历描述、项目描述）附带来源标签：
标签
含义
展示方式
user_input
用户手工输入
无标记
user_confirmed
模型建议、用户已确认
无标记，但保留审计记录
llm_draft
模型生成、用户尚未确认
黄色草稿态标记  + " 待确认 " 提示
llm_augmented
模型基于用户输入扩充的内容（含新增数据）

（2）事实锚定提示词约束。 系统提示词中明确禁止模型补充用户未提供的事实性信息，具体包括：公司名称、职位名称、时间区间、学历学位、证书名称与分数、项目名称、可量化数据。当用户要求"帮我写得更丰富"时，模型必须先输出追问清单，而非直接生成。
（3）量化数据回填确认。 当生成内容中出现数字（百分比、金额、人数、时长）而这些数字未出现在用户原始输入中时，系统必须将该处标记为"待核实"，并在用户确认前以占位形式呈现（例如"提升 __%"），禁止模型直接填入看似合理的数值。
（4）审计留痕。 每次生成记录模型、提供商、提示词版本、输入上下文哈希、输出内容、用户决策（采纳/修改/拒绝）。审计记录用于合规留痕与模型效果分析，但不得包含用户简历全文的可识别存储，仅保留哈希与统计指标。
5.3.4 交互形态
大模型能力通过三种交互形态触达用户，三者共享同一套工具契约与补丁审批机制。
形态一：对话式智能体。 用户以自然语言下达指令，模型返回 JSON Patch 补丁提案，界面以"审批卡片"呈现改动前后对比，用户可逐条批准、修改或拒绝。批准后补丁原子应用并生成版本快照，拒绝则丢弃提案。此形态适合复杂、跨分区的编辑需求。
形态二：行内润色。 用户选中某段文字，浮出工具条提供固定动作：更简洁、更专业、补充量化、STAR 化、去 AI 味。点击后直接以原段落的改写版本替换，撤销可回退。此形态适合快速微调。
形态三：一键诊断与批量优化。 用户点击"简历诊断"，系统输出分项评分与改进建议清单，每条建议附"一键修复"入口。批量优化是一次性生成多项补丁提案，用户可在统一界面中逐条审批。此形态适合初稿质量较低的场景。

以"分段经历改写"为例，完整时序如下：
用户选中经历描述 → 点击"补充量化"   │   ├─ 前端组装请求：选中文本 + 简历上下文摘要 + 目标岗位（若有）   │   ▼业务能力层校验：登录态、AI 提供商可用性、配额余量、限流   │   ▼提示词服务组装：系统提示词 + 上下文（画像/JD/知识库）+ 用户指令   │   ▼内容安全预检：对用户输入做敏感内容检测   │   ▼大模型调用（流式）   │   ├─ 模型返回候选改写文本，或返回追问清单   │   ▼内容安全后检：对模型输出做合规检测与事实性数字检测   │   ▼构造补丁提案：目标路径 + 改动前后值 + 来源标签 + 待核实标记   │   ▼前端展示审批卡片 → 用户批准   │   ▼应用补丁 → 生成版本快照 → 记录审计 → 触发计数器扣减

7 大模型能力设计
本章定义模型选型与路由策略、容错降级机制、成本控制手段与提示词工程规范四项工程约束。
7.1 模型选型与路由
系统采用多提供商抽象层，不绑定单一模型。按场景与成本分层路由。
档位
适用场景
候选模型
路由策略
低档（抽取 / 分类）
技能标签抽取、字段归一化、 JD  关键词提取
中小参数通用模型
优先本地或低成本模型

分段改写、 STAR  扩写、自我评价、翻译

按提供商可用性与时延择优

强推理模型

提供商策略：国内场景默认优先接入国内已完成备案的模型服务，确保合规与网络可达性；私有化部署场景允许接入本地推理服务。

故障场景
降级策略
首选模型超时
自动切换同档位备用提供商，重试一次
全部提供商不可用
返回明确提示，保留用户输入，不丢失上下文
模型输出结构不合法
触发一次 " 修复重试 " ，仍失败则返回原始文本供用户手工处理

7.3 成本控制
分层路由：能用低档模型完成的场景不调用高档模型；
提示词缓存：系统提示词与知识库片段启用缓存，减少重复输入消耗；
结果缓存：对相同输入哈希的请求在短时间窗口内复用结果；
上下文裁剪：按分层裁剪策略控制输入长度；
流式输出：用户可提前中止不满意的生成，减少无效 token；
成本看板：按场景、模型、用户维度监控成本，设定日/月阈值告警。

10 合规与内容安全设计
本章是系统的合规基线，定义三个强制控制点、内容安全检测策略，以及针对简历真实性与代写风险的产品立场。
10.1 合规控制点
系统在三个位置设置强制控制点。
控制点一：数据采集层
所有个人信息字段标注采集目的与必要性；
性别、民族、婚姻状况默认不采集、不展示，若用户主动填写则明示"选填，不用于筛选"；
提供数据导出与彻底删除能力，删除操作需覆盖主表、版本快照、上传文件、统计数据与日志中的可识别信息；
未成年人用户不提供 AI 生成能力。
控制点二：模型调用层
用户简历内容不得用于模型训练。调用第三方模型服务时，需选择承诺不将输入数据用于训练的接口，或使用私有化部署模型；
不向模型传递超出当前任务必需范围的信息（例如生成自我评价时无需传入完整联系方式）；
输入与输出均经过内容安全检测，检测结果留痕；
涉及"具有舆论属性或社会动员能力"的算法能力（如岗位推荐）需按要求开展安全评估与算法备案。
控制点三：内容输出层
AI 生成内容在数据库中以来源标签标注；
导出物按《人工智能生成合成内容标识办法》要求保留生成标识能力；
生成内容不得包含民族、性别、年龄、地域等歧视性表述，提示词中明确禁止条款；
提供便捷的投诉举报入口。

10.3 简历真实性与代写风险
这是本产品特有的伦理风险。系统采取以下立场与措施：
系统定位为"放大器"而非"代笔"：所有生成内容以用户的真实经历为输入，系统优化的是表达结构而非事实本身；
禁止编造：提示词层面硬性禁止补充用户未提供的事实；
草稿态呈现：未确认的生成内容在界面上以草稿态展示，提示用户核对；
待核实标记：不可溯源的数据以占位形式呈现，要求用户填写真实数值；
使用协议明示：用户协议中明确说明用户对简历内容真实性负责，系统不承担内容真实性担保。
